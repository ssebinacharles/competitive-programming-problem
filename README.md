# Adversarial Problem: Maximum GCD XOR

This repository contains a Codeforces Div1/Div2-level problem: given an
array, find the maximum value of `gcd(subarray) xor xor(subarray)` over
all non-empty subarrays.

The optimal solution uses:
- The classic observation that there are only `O(n log A)` distinct gcd
  values among subarrays ending at any fixed right endpoint, maintained
  as a small list of `(gcd, leftmost-L)` pairs as the right endpoint
  advances.
- A persistent binary trie over prefix-XOR values to answer, for each
  gcd interval `[L, R]` of left endpoints, the maximum XOR of
  `gcd xor prefix[i]` over `i` in that range in `O(30)` per query.
- Overall complexity `O(n log A * B)` time, `O(n * B)` memory, where
  `B = 30` is the bit width — comfortably inside `n <= 2*10^5`, 3s, 256MB.

## What's here

- `problem.md`, `idea.md`, `solution.md` — statement, design rationale,
  and algorithm writeup.
- `solution.cpp` — accepted reference solution.
- `solution_bf.cpp` — O(n^2) brute force **for this problem** (enumerate
  every subarray, track running gcd/xor). Used to stress-test
  `solution.cpp`.
- `generator.cpp` — random test generator for this problem's input
  format (`./generator <seed> <maxN> <maxA>`). Small `maxA` produces
  lots of repeated values, ties, and `a_i = 0` cases, which stress the
  distinct-gcd interval logic harder than large random values do.
- `test_cases/` — 7 cases:
  - `1`–`5`: the original hand-picked/small cases (worked example, single
    element, ties, all-equal array, powers of two).
  - `6`: **large performance test**, `n = 2*10^5` with values spread
    across the full `[0, 2^30)` range — this is the case that actually
    forces the O(n^2) attempt to time out. (An earlier version of this
    submission mentioned "a large hidden case used by the judge" without
    actually including one; this has been fixed by adding it here.)
  - `7`: a small, hand-checkable counterexample (`[25, 21, 6, 21]`) that
    exposes the greedy-early-break bug in `qwen/solution_02.cpp` and,
    incidentally, also the off-by-one bug in `qwen/solution_03.cpp`.
- `qwen/` — three simulated flawed attempts, each **compiled and actually
  run** against every file in `test_cases/` to confirm it fails at least
  one (see `qwen/conversations.md` for exact commands and outputs, plus
  an honest note about not having real access to chat.qwen.ai):
  1. `solution_01.cpp` — correct logic, O(n^2) — fails via TLE on test 6.
  2. `solution_02.cpp` — incorrect greedy early-break — fails (wrong
     answer) on tests 6 and 7.
  3. `solution_03.cpp` — off-by-one in the persistent-trie query range —
     fails (wrong answer) on tests 3, 5, and 7.

## Verification performed

- `solution.cpp` was stress-tested against `solution_bf.cpp` over 800+
  random cases (small n, small value ranges to force ties/repeats) with
  no mismatches, plus a separate check with larger n and the full value
  range.
- `solution.cpp` was timed at `n = 2*10^5`: ~0.4s locally, well inside
  the 3-second limit.
- All 7 official test cases were generated by running `solution.cpp`
  itself; cases 1–5 and 7 were additionally cross-checked against
  `solution_bf.cpp`.
- All three `qwen/` attempts were compiled and run against the full test
  suite; each fails at least one case (see `qwen/conversations.md`).
